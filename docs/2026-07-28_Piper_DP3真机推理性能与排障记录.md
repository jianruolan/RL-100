# 2026-07-28 Piper DP3 真机推理性能与排障记录

## 1. 结论

目标权重：

```text
RL-100/data/outputs/
  piper_pick_and_place_augmented_chunk4_control_clean_dp3_
  episode10_bs64_epoch4000_seed42/
```

的总参数量为约 **70.79M**，其中 diffusion UNet 为 **70.72M**，点云编码器仅为约
0.064M。它在 NVIDIA Thor 上使用当前的 10-step DDIM 推理时，纯策略推理约为
132--138 ms，即约 **7.5 Hz**；因此无法在每个 66.7 ms 的 15 Hz 控制周期内生成一条
新策略动作。

这不是 Piper CAN 通信或点云构建造成的。历史真机日志与今天的离线 Thor 基准一致：控制
loop 可维持 15 Hz，但异步策略 worker 每秒只能完成约 7.3--7.5 个新的 action chunk。

真机“动作慢”还受执行侧限速影响，不能全部归因于模型。今日部署脚本默认把关节规划器
限制在 0.15 rad/s、0.20 rad/s²；这本身会显著拉长一段关节位移的完成时间。

## 2. 权重和推理配置

训练配置来自 checkpoint 内的 Hydra config：

| 项目 | 值 |
| --- | --- |
| policy | `RL1003D` / 标准 DP3 |
| action | 7 维绝对关节目标（6 关节 + 夹爪开合命令） |
| 观测 | 3 帧 `point_cloud(512,3)` + `agent_pos(7)` |
| horizon / action steps | 6 / 4 |
| DDIM inference steps | 10 |
| `down_dims` | `[256, 512, 1024]` |
| diffusion time embedding | 256 |
| image backbone | `null`，该 checkpoint 实际不使用 RGB encoder |
| 总参数 | 70.7876M |
| UNet 参数 | 70.7238M |

模型每次 `predict_action` 先执行一次点云/状态编码，再在 DDIM 采样循环中调用 UNet
10 次。因此主要计算量来自宽度为 256/512/1024 的 UNet 被重复执行，而非 512 点点云。

## 3. Thor 实测性能

测试输入为 clean Zarr 的真实连续三帧观测；每项均在 Thor GPU 上预热后多次运行，包含
CUDA 同步，不连接 RealSense、Piper 或 CAN。

| 架构或采样设置 | 参数量 | 平均耗时 | P95 耗时 | 纯推理频率 |
| --- | ---: | ---: | ---: | ---: |
| 当前模型，10 DDIM steps | 70.79M | 132.3--134.5 ms | 138--139 ms | 7.4--7.6 Hz |
| 当前模型，5 DDIM steps | 70.79M | 67.0 ms | 68.0 ms | 14.9 Hz |
| 当前模型，3 DDIM steps | 70.79M | 41.5 ms | 42.4 ms | 24.1 Hz |
| 当前模型，1 DDIM step | 70.79M | 16.1 ms | 17.6 ms | 62.1 Hz |
| 当前模型，10 steps + FP16 autocast | 70.79M | 157.0 ms | 264.3 ms | 6.4 Hz |

结论：

- 15 Hz 的总预算是 66.7 ms；当前 10-step 模型单独就超过预算约两倍。
- 5 steps 仅勉强达到纯模型 15 Hz，没有足够的相机、点云、Python 调度和 CAN 余量。
- 3 steps 有端到端余量，但必须通过离线和真机 A/B 验证动作质量是否下降。
- 此环境的 FP16 autocast 未加速，反而变慢；不要在没有实测的情况下把它当成部署优化。

## 4. 历史真机日志佐证

同一 chunk-4 epoch-4000 模型的无平滑执行日志显示：

| 指标 | 典型值 |
| --- | ---: |
| 请求控制频率 | 15.00 Hz |
| 实际控制 loop | 15.00 Hz |
| 新策略结果完成频率 | 7.3--7.4 Hz |
| 单次策略推理 | 135--137 ms |
| 点云/观测构建 | 约 2.4--2.9 ms |
| 执行动作平均 policy age | 约 3.55 个 15 Hz step |

部分后续平滑实验出现约 200--317 ms 的单次推理记录（约 3.2--5.0 Hz）。这表明设备负载、
功耗/时钟状态或运行时调度可能进一步恶化延迟；但当前 132--138 ms 的稳定基线已经足以
解释 10-step 模型不能达到 15 Hz。

## 5. 异步控制的实际含义

当前部署采用异步 policy worker：控制线程仍按 15 Hz 发送规划后的动作；worker 忙时，
新观测请求会替换尚未开始的旧请求。因此：

```text
控制发送：15 Hz
策略请求：15 Hz
新策略 chunk 完成：约 7.5 Hz
执行内容：旧 chunk 的后续动作 / temporal ensemble
```

这能避免控制 loop 因 diffusion 阻塞而降频，但不能消除新观测到新策略动作之间的延迟。
对于快速抓取阶段，过期 chunk 会表现为反应迟缓或对物体位置变化不够敏感。

## 6. 真机速度的独立限速因素

今日新增的 `tools/teleop_off2off_data/infer_proprio_piper_last.py` 默认参数为：

```text
--speed-percent 10
--max-joint-speed-rad-s 0.15
--max-joint-accel-rad-s2 0.20
--max-gripper-speed-m-s 0.02
```

这组值是安全起点，不是性能最大值。以 1 rad 位移估算，0.15 rad/s 的上限本身就需要
约 6.7 s 的匀速时间，另加约 0.75 s 的加速时间。故应分别评估：

1. 政策更新频率：由模型大小和 DDIM 步数决定；
2. 物理执行速度：由 planner 速度/加速度上限、Piper `speed_percent` 和跟踪误差决定；
3. 平滑/夹爪同步：会为连续性和安全主动牺牲速度。

在确认工作区和碰撞边界后，可从历史平滑实验已经使用过的 0.35 rad/s、0.8 rad/s²
量级开始逐步评估，不应直接把规划器上限改为极大值。

## 7. 设备状态与排障结论

今日只读检查结果：

- Thor 处于 120W power mode；
- 采样时 GPU / TJ 温度约 47.8°C；
- 非 root 用户不能调用 `jetson_clocks --show`；
- `tegrastats` 空闲采样时 GPU 负载不代表训练或推理满载时频率，因此不能据此宣称时钟已锁定。

当前优先级不是先猜测热降频，而是先解决已量化的 10-step 计算预算问题。后续真机 A/B
应同时记录 inference latency、policy age、loop Hz、GPU 频率/温度及真实关节速度。

## 8. 后续路线

1. 训练较小 UNet，并保持 10 DDIM steps，先隔离“容量”变量；
2. 对最优小模型评估 10 / 5 / 3 DDIM steps；
3. 真机上分别比较成功率、完成时间、动作平滑度、policy age 和实际推理频率；
4. 若 3--5 steps 明显降低质量，训练 consistency/LCM distilled student，而非对当前
   checkpoint 直接设 `use_cm=True`；当前权重没有已训练的 distilled model，不能直接一键
   变成一步 consistency 推理；
5. 若必须保留大模型质量，另行评估 TensorRT/图编译；但这不能保证将 132 ms 压至 66 ms，
   且 FP16 autocast 已证明不是现成解法。

## 9. 今日部署脚本适配与观测一致性

今日已直接修改：

```text
tools/teleop_off2off_data/infer_proprio_piper_last.py
```

适配过程没有 import 仓库中的其他推理脚本，而是沿用该脚本自身的推理、Piper 通信、
控制和安全逻辑完成。关键修正包括：

- 从 checkpoint 读取 Hydra 配置，并严格加载 EMA policy；
- 按训练定义构造连续 3 帧 `point_cloud(512,3) + agent_pos(7)`，而不是把该模型误当成
  proprio-only policy；
- 在脚本内部复现训练集使用的 D435i depth optical frame 点云处理；
- 保留 Piper 通信、轨迹规划、安全 hold、异步推理和 temporal ensemble；
- 离线 smoke test 已得到形状为 `(4, 7)` 的 action chunk，证明 checkpoint、输入和输出
  接口可以闭环。

这里最重要的经验是：文件名里的 `proprio` 不能代替 checkpoint 的实际配置。部署时应以
checkpoint 的 shape meta 和训练数据预处理为准，否则脚本即使能够运行，也可能是在给模型
错误的观测分布。

## 10. 今日控制策略迭代中的问题与经验

### 10.1 平滑、时序融合和位姿同步解决的是不同问题

- trajectory smoothing 限制速度、加速度和 jerk，主要抑制高频关节抖动；
- temporal ensemble 融合不同预测时刻对当前动作的估计，主要缓和 chunk 边界和动作陈旧；
- gripper pose-sync 在机械臂姿态稳定后再允许夹爪阶段切换，主要减少“手臂还未到位、夹爪已
  切换”的阶段冲突。

三者可以叠加，但都会引入响应延迟或保守性，也都不能提高 diffusion 网络本身的吞吐率。
今日后期日志中，即使启用 temporal ensemble，新推理完成频率仍常见约 4--5 Hz，不能把
控制输出看起来连续等同于模型已经达到 15 Hz。

### 10.2 chunk-8 首次真机运行异常不能作为效果结论

`pick_place_chunk8_epoch4000_nonsmooth_execute_01.json` 只有 3 条记录并以
`exception_hold` 结束。该文件只能作为启动异常/安全保持记录，不能用于评价 chunk-8 的
任务效果。后续 `_02` 和带平滑、时序融合、位姿同步的运行才提供了可分析的连续轨迹，但
这些 JSON 同样没有人工成功标签。

### 10.3 续训状态必须从 checkpoint 核验

chunk-4 的 4000→6000 续训曾被要求停止。仅看中间生成的 epoch-5200 文件容易误判为在
5200 左右中断；最终 `latest.ckpt` 的 payload 显示 `epoch=6000`、
`global_step=60000`，且检查时已无对应训练进程。经验是：训练是否完成应联合检查进程、
日志尾部和 checkpoint 内部 epoch/global step，而不能只看某个周期 checkpoint 的文件名。

### 10.4 后台训练要同时验证“会话存在”和“进度在增长”

紧凑模型训练最初出现过重复启动痕迹，之后使用 detached tmux 队列统一串行调度，并设置
30 分钟监视日志。仅看到 tmux session 不代表训练健康；监控至少应检查：

1. `train.py` PID 和启动参数是否唯一且正确；
2. `latest.ckpt` 修改时间和 epoch 是否持续增长；
3. 日志是否出现 OOM、Hydra 配置错误、CUDA 异常或非零退出；
4. 前一模型失败时是否阻止后一模型继续启动。

## 11. 记录与结论边界

今日的真机 JSON 记录了控制配置、轨迹、运行时长、推理时延和停止原因，但没有人工标注的
抓取成功、放置成功或完整任务成功字段。因此本文不从记录条数、运行时长或
`operator_hold` 推导成功率。后续比较 4000/6000 epoch、chunk-4/8、RGB/点云以及不同
紧凑模型时，应采用固定场景和人工结果表，至少标记抓取、搬运、放置三个阶段。
